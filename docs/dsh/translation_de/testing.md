# Test-Richtlinie

English | [中文](testing.zh.md)

Wie dieses Repository testet, Ebene für Ebene, und die Regeln, die eine grüne Suite aussagekräftig halten. Befehle stehen in der Root-[AGENTS.md](../AGENTS.md); verlinkte Agent Notes tragen die Begründung.

## Ebenen

- **Unit** (`pnpm run test`): vitest über Package- und Example-Specs unter deren Verzeichnissen `tests/**` sowie über Repository-Script-Specs unter `scripts/**/*.spec.ts`; Tests bleiben in dem Code-Bereich, den sie prüfen. Jede Registry erhält einen HMR-Sicherheitstest (den beitragenden Fiber disposen, Cleanup prüfen). Randfälle, Fehlerpfade, Event-Reihenfolge, Nebenläufigkeits-Races und dauerhafte Tests für Vertragsregressionen bevorzugen (siehe `packages/core/agent-loop/tests/contract-regressions.spec.ts`).
- **Coverage-Gate** (`pnpm run test:coverage`): der Gate-Lauf, 100 % pro Datei auf `packages/*/*/src`. Eine nicht abgedeckte Zeile ist oft toter Code, den das Gate zur Löschung markiert, kein fehlender Test zum Nachrüsten. Zeilen-Coverage ist notwendig, nie ausreichend — sie belegt, dass Zeilen liefen, nicht dass das Feature wie ausgeliefert funktioniert. 100 % pro Datei auf `packages/shell/pwsh-local/src` erfordern ein echtes `pwsh`: ohne dieses überspringen sich seine Executor-Suiten selbst, und `vitest.config.ts` nimmt die Datei aus, damit Hosts ohne pwsh grün bleiben, während CI-Runner pwsh mitbringen und die volle Messlatte durchsetzen.
- **Real-API-e2e** (`pnpm run test:e2e`): Tests mit Key gegen Live-Provider-APIs — das DeepSeek-Modell plus Provider-spezifische Smokes, die über ihre eigenen Keys gaten (`EXA_API_KEY`, `PERPLEXITY_API_KEY`, …); jede Suite überspringt sich ohne ihren Key selbst, damit CI ohne Keys grün bleibt ([Real-API-e2e-Agent-Note](../.agents/notes/implemented/testing/2026-06-19-real-api-e2e-ci.md)).
- **Owner-lokale erwartete Ausgabe** (`pnpm run test:expected`): zusammengesetzte CLI-/Prozess-Erwartungen ohne Key und ohne Roundtrip über eine aufgezeichnete Session. Driver verwenden `*.expected.e2e.ts` neben `tests/expected/`; CI führt gebaute Exporte aus. Package-/Script-Erwartungen verwenden `test`, Browser-Erwartungen verwenden `test:web`.
- **Performance-Benchmarks** (`pnpm run test:bench`; erforderliches Linux-PR-Gate `node 24 / benchmarks`): `benchmarks/` gruppiert Gates für Nutzerpfade. Es baut Bibliotheken und Worker; zeitlich gemessener Code läuft unter plain Node, niemals unter TSX. Synthetische Eingaben erzwingen Zeit-, Heap- und Skalierungsbudgets; paketlokale `.perf.ts` bleiben diagnostisch ([Regeln](../.agents/notes/implemented/testing/2026-09-04-session-open-performance-gate.md)).
- **Snapshot** (`pnpm run test:snapshot`): die höchste aufgezeichnete Parent-Generation eines Top-Level-Szenarios liefert Nutzereingabe und Modell-Replay und dient anschließend als erwartetes persistiertes Ergebnis. Parent-Dateinamen sind `session[.vN].jsonl`; Child-Rollen sind `session.<ordinal>[.vN].jsonl`; v0 lässt `.v0` weg, positive Versionen erfordern kleingeschriebenes `.vN`, und jeder Dateiname muss mit seinem Header übereinstimmen. Prozess-Szenarien starten über `dsh`: Headless besitzt das One-Shot-Verhalten, das SDK die persistente Steuerung, ACP das Verhalten des Automatisierungsprotokolls, und Web behält Browser-/ARIA-Nachweise neben derselben Session. `snapshot.yml` deklariert das Profile, die Composition-/Header-Klasse, die Aufzeichnungsrichtlinie, exceptionelles Replay oder Eingabe-Metadaten und Workspace-Fakten. Typisierte Tokens erhalten die Identitätsbeziehungen zwischen Parent und Child; nur Header-Pins besitzen Prompt-/Schema-Sidecars. Ein mutierendes Szenario vergleicht unabhängig den vollständigen Baum `workspace.expected/`, den Record und Refresh niemals neu schreiben. `test:snapshot:record` verwenden, wenn sich ein Modell-Transkript ändert, und `test:snapshot:refresh`, wenn die Replay-Eingabe gültig bleibt; jeden resultierenden Diff prüfen.
- **Web-Browser-Snapshot** (`pnpm run test:web`; erforderliches Linux-PR-Gate): Der Befehl baut das Plugin-CSS und vergleicht dann alle session-getriebenen Ausgaben aus `snapshots/web/` und die reinen UI-Ausgaben aus `apps/web/tests/expected/` in Chromium; die Modell-/Reasoning-Auswahl läuft zusätzlich in WebKit. CI erzwingt das schreibgeschützte `DSH_SNAPSHOT=replay`; Record/Refresh bleiben lokal, wobei jeder Diff geprüft wird ([Web-Lane](../.agents/notes/implemented/testing/2026-07-24-web-gui-browser-e2e-lane.md), [CI-Referenz](../scripts/run-web-snapshots.ts)).

Session-Fixtures behalten Header und Payloads, lassen aber Body-Sequenz-/Zeit-Envelopes weg; Replay synthetisiert sie. Replay, Record und Refresh wählen die höchste Generation jeder Parent-/Child-Rolle. Aktuelle Fixtures verwenden das [Writer-Format](session-format-status.md) in ihren Dateinamen und Headern, eine Zeile pro Event und eingebettete kompakte Assistant-Streams. Historische Fixtures behalten ihre veröffentlichte Repräsentation; explizite `sessionFormat`-Owner erhalten die Migrationsabdeckung. Dem [Format-Version-Cookbook](cookbook/adding-a-session-format-version.md#snapshot-successors) folgen, um Nachfolger hinzuzufügen, ohne Vorgänger zu ändern.

## Wie Specs ausgeführt werden

Geforkte Worker führen mehrere Spec-Dateien gleichzeitig aus, das Coverage-Gate teilt sich in seinem Job in nebenläufige Partitionen neben den übrigen Gates auf, und die selbst gehosteten Runner teilen sich einen Host und ein Volume. Isoliert ist nur der Prozess: Ports, vorhersagbare Pfade, externe Namespaces und geerbte Child-Prozesse sind es nicht. Jede erworbene Ressource bis zum Teardown selbst verantworten. Eine Spec, die nur allein besteht, hat einen Testdefekt, keinen instabilen Runner. [dsh-ci-test-reliability](../.agents/skills/dsh-ci-test-reliability/SKILL.md) besitzt die Regeln zu Allokation, Wiederherstellung, Synchronisierung, Timeout-Budget, Plattform und Teardown; ihr [Workflow zur Flake-Diagnose](../.agents/skills/dsh-ci-test-reliability/references/ci-flake-diagnosis.md) klassifiziert einen bestehenden probabilistischen Fehler. [Unerwartete Fork-Exits](../scripts/coverage-fork-diagnostics.ts) melden PID, Datei, Code und Signal.

## Die Richtlinie für Tests mit Key: Inferenz ist hier günstig

Wir sind DeepSeek — Real-API-Tests nicht rationieren. Ein Test ohne Key belegt die Verkabelung; nur ein Lauf mit Key belegt, dass der Agent gegen ein echtes Modell funktioniert. Dateischreibende Prompts, Multi-Turn-Konversationen, Tool-Nutzung und Abbruch mitten im Stream abdecken. Am wertvollsten sind **Smoke-Tests**, die ein ausgeliefertes `dsh`-Profile booten, einen Prompt senden und die Welt prüfen — sie fangen die Klasse „grüne Unit-Tests, kaputtes Produkt“ ab, die Mocks nicht erreichen ([Postmortem 0001](postmortem/0001-acp-default-export-drops-inject.md)). Self-Skip hält CI ohne Secrets und Beitragende ohne Keys lauffähig; es ist kein Kostensignal. Integrationstests auf Profile-Ebene liegen unter `apps/cli/tests/profiles/`; paketspezifische Kompositionen bleiben bei den Tests ihres Pakets.

## Die echte Implementierung einem Mock vorziehen

Nur die teure oder nichtdeterministische Grenze mocken (LLM-Adapter, Netzwerk, Uhr); alles Nachgelagerte echt halten. Ein selbstgebauter Ersatz belegt, dass die Bridge Bytes bewegt, nicht dass das ausgelieferte Tool sich wie behauptet verhält. Bridge-Tool-Aufruf-Tests behalten die echte Tool-Registry und Pipeline hinter dem geskripteten Mock-Modell: `makeBridgeHarness()` mountet den Agent-Loop, den Session-Store, die Tool-Registry und die JSONL-Persistenz mit einem `MockAdapter` als einzigem Mock (packages/acp/acp/tests/harness.ts).

Recovery-Tests unterscheiden Pre-/Post-Chunk-Fehler nach Schritt und belegen, dass fehlgeschlagene Chunks keine Message- oder Tool-Seiteneffekte ableiten. Erschöpfung, Abbruch, Policy-Komposition, Persistenz, Status, Wire-Zähler, Idle-Timeouts beim Schließen des Transports und die Komposition des ausgelieferten Loaders abdecken.

## Die Welt prüfen, nicht den Selbstbericht

Eine e2e-Assertion führt den Befehl erneut aus oder liest die Datei extern erneut; eine Keyword-Sonde auf der eigenen Ausgabe des Agenten lässt einen betrügenden Agenten bestehen. Zusichern, dass unberührte Dateien byte-identisch sind. e2e-Tests besitzen ihre Ressourcen: im Test anlegen, in `afterEach` disposen (auch bei Fehler/Retry/Timeout); gemeinsame Fixtures liegen in einer einfachen `tests/harness.ts`, niemals in einer weiteren `*.e2e.ts` (der Import einer Spec registriert deren `describe` erneut und dupliziert echte API-Aufrufe).

## Den echten Einstiegspfad testen

- Produktsichtbare Plugins erfordern einen REAL-Kompositionstest außerhalb der Unit-Ebene. Von Hand gebaute `ctx.plugin(...)`-Suiten genügen nicht: eine nur für Tests bestimmte `cordis.yml` über Loader und App/Prozess booten, nur externe Services oder nichtdeterministische Eingaben mocken und den modellsichtbaren Request/Log, den dauerhaften Zustand oder die nutzersichtbare Ausgabe zusichern. Opt-ins aus den ausgelieferten Defaults heraushalten.
- Eine Guard schützt nur, wenn die Regression sie scheitern lässt. Bei einem Plugin ohne `inject` (Bundle-/Kompositions-Plugins) bleibt ein Loader-Smoke grün, wenn ein Default-Export die erforderlichen Named Exports ersetzt — eine explizite Assertion `expect('default' in mod).toBe(false)` plus eine `unwrapExports`-Roundtrip-Assertion ergänzen und belegen: die Regression einbauen, rot beobachten, zurücknehmen.
- „Echter Einstiegspfad“ meint das veröffentlichte Artefakt: ein `bin` eines Pakets führt gebautes `lib/bin.js` unter plain `node` aus und legt damit Fehler offen, die tsx verdeckt (Settle-Races, Modulauflösung, verschluckte Ladefehler). Dasselbe gilt für Nicht-Index-Runtime-Einstiege (der Node-Programm-Bootstrap `lib/process.js`) und für Singleton-Module, die über Bundles hinweg geteilt werden (`packages/sdk/server/tests/built-scope-carrier.e2e.ts`). Die Smokes für gebaute Artefakte grün halten (`packages/examples/*/tests/built-bin.e2e.ts`, `packages/ptc-runtime/ptc-runtime-node/tests/built-lib.e2e.ts`) und zusichern, dass eine wirklich fehlende Config mit einem Exit-Code ungleich null beendet.

## Test-Auflösung: nur die Source-Ebene

- Jede vitest-Config richtet vite-tsconfig-paths auf `tsconfig.base.json`; bloße Workspace-Imports werden zu `src` aufgelöst ([Layout](development.md#typescript-project-layout)), niemals über die `exports` eines Pakets zu gebautem `lib/` — veraltete Artefakte dort laden eine zweite Kopie von Modul-Singletons. Gebaute Artefakte werden nur explizit konsumiert: Subprozesse im `lib`-Modus und die gebauten Smokes unten.

## Startmodi von Test-Subprozessen

- CI und Test-Lanes mit Build führen jeden Profile- oder Cordis-Config-Subprozess aus gebautem `lib/` über den gemeinsamen Dual-Mode-Launcher aus. Für diese Subprozesse `--import tsx` nicht von Hand schreiben.
- Protokoll- und Betriebssystem-Fixtures, die Cordis nicht laden, führen löschbares `.ts` direkt mit Node aus, ohne tsx und ohne die Root-Paths-Map.
- Nur ein Test, dessen Gegenstand die Auflösung von Source-Pfaden ist, darf `src` wählen; dieser Vertrag ist im Test anzugeben.

## Wann ein Snapshot-Test erforderlich ist

Jede nicht triviale modell-, protokoll- oder menschensichtbare Änderung fügt im selben PR ein Szenario mit aufgezeichneter Session ohne Key hinzu oder aktualisiert es; Package-, e2e-, reine Mock- und Begründungsnachweise ersetzen das zusammengesetzte Transkript nicht. Aufzeichnungen für Headless, SDK, ACP und Web liegen unter `snapshots/session/`, `snapshots/sdk/`, `snapshots/acp/` und `snapshots/web/`; ein Web-Rendering darf ausdrücklich die kanonische Session eines anderen Szenarios ausleihen. Erwartete Ausgabe, die nicht von einer aufgezeichneten Session getrieben ist, bleibt bei ihrer besitzenden App, ihrem Paket oder Script unter `tests/expected/` und verwendet nicht das Suffix `*.snapshot.ts`. [`dsh-session-snapshot`](../packages/test-support/session-snapshot/README.md) besitzt die gemeinsamen Speicherregeln und Profile-Adapter. Änderungen an Agent-Loop, Session-Lifecycle und `SessionEventMap` aktualisieren beide SDK-Projektionen: `snapshots/sdk/` besitzt TypeScript, während die [Python-Runtime-CI](../.github/workflows/ci-master.yml) `scripts/snapshots/python-sdk-single-exe/` besitzt. Neue Capability-Seams und Lifecycle- oder Transkript-Varianten benennen zur Planungszeit jede erforderliche Ebene.
