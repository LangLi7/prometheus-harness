# Zweisprachige Dokumentation

English | [中文](README.zh.md)

Die Dokumentation dieses Repos wird von Menschen und Agents innerhalb und außerhalb des Unternehmens gelesen; daher wird jedes Dokument im Geltungsbereich in Englisch und in vereinfachtem Chinesisch gepflegt. Diese Seite definiert den Paarungsvertrag, die Prüfungen, den Geltungsbereich und die Ausnahmen; [translation-rules.md](translation-rules.md) definiert, wie übersetzt wird; [terminology.md](terminology.md) ist die maßgebliche Quelle der Terminologie. Routinemäßige Agent-Arbeit folgt dem leichten Pfad in [docs/AGENTS.md](../AGENTS.md); der erweiterte Workflow [.agents/skills/dsh-translate-docs](../../.agents/skills/dsh-translate-docs/SKILL.md) steht nur über explizite Nutzeraufforderung zur Verfügung.

## Der Paarungsvertrag

- **Beide Sprachen tragen gleiche Autorität.** Ein Dokument darf zuerst in einer der beiden Sprachen verfasst und geprüft werden — eine zuerst auf Chinesisch verfasste Agent Note ist ebenso legitim wie eine zuerst auf Englisch verfasste — und das Gegenstück wird daraus übersetzt. Keine der beiden Dateien rangiert über der anderen; was sie bindet, ist die Anforderung, dass beide dasselbe aussagen.
- **Ein Paar besteht aus drei Geschwisterdateien.** Die englische `foo.md`, die chinesische `foo.zh.md` und ein Konsistenzprotokoll `foo.i18n.yaml`, alle im selben Verzeichnis. Keine Locale-Verzeichnisse, kein separates Übersetzungs-Repo, keine verschachtelten zweisprachigen Dateien. Paare werden als Ganzes zusammengeführt: Ein PR landet niemals eine Sprache ohne die beiden anderen Dateien.
- **Das Konsistenzprotokoll.** `foo.i18n.yaml` enthält einen Eintrag je Überschriftabschnitt, der noch sprachspezifischen Inhalt enthält. Der Schlüssel ist der englische Überschrift-Slug-Pfad des Abschnitts (`/` für Text vor der ersten Überschrift; ein wiederholter Pfad erhält `~2`, `~3`, …), und der Eintrag enthält einen Hash der englischen und der chinesischen Blöcke in diesem Abschnitt, die sich zwischen beiden Seiten unterscheiden:

  ```yaml
  /foo:
    en: 41d772192075e133
    zh: dda91c6c670cfd9d
  /foo/usage:
    en: 86940bea4a3c7ed6
    zh: de78429597783c7f
  ```

  Abschnitt `i` der einen Seite entspricht Abschnitt `i` der anderen. Der Hash jeder Seite umfasst jeden Block der obersten Ebene des Abschnitts außer fenced Code Blocks und generierten Bereichen — den beiden Inhaltsarten, deren Gleichheit auf beiden Seiten die Prüfung bereits verlangt; Inhalt, der lediglich zufällig identisch ist, wird dennoch gehasht. Ein Abschnitt ohne verbleibende Blöcke hat keinen Eintrag. Das Neugenerieren eines Bereichs oder das Bearbeiten eines Code Blocks auf beiden Seiten lässt das Protokoll unverändert, und Bearbeitungen unterschiedlicher Abschnitte ändern getrennte Protokollzeilen, sodass Git's Standard-Text-Merge, einschließlich dem von GitHub, sie zusammensetzt. Ein Protokoll gerät nur dann in Konflikt, wenn beide Branches gehashten Inhalt im selben Abschnitt geändert haben; in diesem Fall das Markdown auflösen und das Paar neu protokollieren. Ein nicht synchronisiertes Paar wird aktualisiert, indem das Gegenstück minimal gegen den Diff der bearbeiteten Seite gepatcht wird, niemals durch Neuübersetzung ganzer Dateien; die Prüfung benennt jeden geänderten Abschnitt. Routinearbeit nimmt diesen Patch direkt vor; wenn der Nutzer den erweiterten Workflow ausdrücklich aufruft, gewinnt `pnpm run gen-translation-brief <pair>` den zuletzt bestätigten Text aus dem neuesten Commit zurück, dessen Inhalte die protokollierten Einträge erzeugen, stellt die Aktualisierung in der engsten sicher ausgerichteten Granularität zusammen, und `--apply` kann eine reine Code-Fence-Änderung nach struktureller Validierung einspleißen. Nachdem das Paar wieder in Übereinstimmung gebracht wurde, protokolliert `pnpm run verify-translation-pairing --write <pair>` die Einträge neu; dieser yaml-Diff ist der prüfbare Akt der Konsistenzbestätigung, weshalb `--write` verlangt, die bestätigten Paare zu benennen (`--write --all` ist die explizite korpusweite Form).

  Die chinesische Datei muss ihren englischen Rücklink behalten; eine verfasste englische Quelle muss ihren chinesischen Link behalten, während eine gelistete generierte englische Quelle ausgenommen ist. Die [archivierte abschnittsschlüsselbasierte Paarungsprotokoll-Agent-Note](../../.agents/notes/archived/process/2026-09-23-section-keyed-translation-pairing-records.md) hält die Formatentscheidung und ihre Alternativen fest.
- **Sprachumschalter.** Die chinesische Datei verlinkt immer unmittelbar nach ihrer H1-Überschrift mit `[English](foo.md) | 中文` zurück. Eine verfasste englische Datei erwidert dies dort mit `English | [中文](foo.zh.md)`; eine gelistete generierte englische Quelle lässt diese Zeile weg, damit sie byte-identisch zur Generator-Ausgabe bleibt. Ein README, das außerhalb von GitHub veröffentlicht wird, etwa PyPI-Projektmetadaten, darf die kanonische URL `https://github.com/deepseek-ai/deepseek-harness/blob/master/<repository-path>` auf dasselbe Gegenstück verwenden, damit der Umschalter auch dort auflöst.
- **Die Struktur spiegelt das Gegenstück.** Überschriftentiefen und -reihenfolge, Listenarten, Startwerte nummerierter Listen, Anzahl der Listeneinträge, Anzahl der Tabellenzeilen und -spalten, semantische Linkziele mit exakten Query-/Fragment-Suffixen und wörtliche Code Blocks stimmen über das Paar hinweg eins zu eins überein. Wenn ein relativer Dokumentlink auf den aktiven zweisprachigen Korpus zielt, verwendet die englische Seite ihren `.md`-Pfad und die chinesische Seite ihren `.zh.md`-Pfad. Ein fehlendes Gegenstück in diesem Korpus ist ein Paar-Vollständigkeitsfehler und kein Rückfall; Ziele außerhalb des aktiven Korpus behalten den verfassten Pfad. Die vollständigen Erhaltungsregeln stehen in [translation-rules.md](translation-rules.md). Bestehende Markdown-Prüfungen gelten unverändert für `.zh.md`-Dateien (`verify-md-wrap`, `verify-md-links`).

## Die Prüfung: verify-translation-pairing

`pnpm run verify-translation-pairing` (Teil von `doc-sync`, das Mitwirkende bei Dokumentationsänderungen lokal ausführen und das CI erschöpfend ausführt) erzwingt den Vertrag mechanisch:

1. Jedes Dokument im Geltungsbereich hat ein vollständiges Paar. Die README-Erkennung erfolgt unabhängig von Groß- und Kleinschreibung des Basisnamens, sodass `missions/readme.md` neben den anderen Dokumentationswurzeln im Geltungsbereich liegt.
2. Jedes überhaupt vorhandene Paar-Artefakt ist vollständig und konsistent: alle drei Dateien vorhanden, das Protokoll ist kanonisch und seine Einträge entsprechen den aus den aktuellen Inhalten berechneten Einträgen (das Ändern sprachspezifischen Inhalts auf einer Seite ohne erneute Bestätigung des Paares schlägt fehl), die chinesische Seite und jede verfasste englische Quelle tragen ihre Sprachumschalter (gelistete generierte englische Quellen sind ausgenommen), jeder gewöhnliche relative Dokumentlink verwendet das Ziel-Locale seiner Quellseite, und die strukturellen Signaturen stimmen in der Reihenfolge überein — Überschriftentiefen, wörtliche Code Blocks (Info-String und Inhalt), Anzahl der Tabellenzeilen und -spalten, Listenarten, Startwerte nummerierter Listen, Anzahl der Einträge und semantische Linkziele mit exakten Query-/Fragment-Suffixen, abgesehen vom Umschalter.
3. Als `excluded` gelistete Dateien haben überhaupt keine `.zh.md` und keine `.i18n.yaml`. Eingefrorene Agent Notes unter `.agents/notes/archived/` liegen außerhalb dieser sich entwickelnden Prüfung; ihr eigener Verifier verlangt und versiegelt stattdessen das vollständige bestehende Triplett.

Quellorientierte Code-Prüfungen konsumieren eine exakte `.zh.md`-Fence-Sequenz als Ableitung ihrer Datei ohne Suffix, anstatt denselben Code zweimal zu kompilieren oder zu manifestieren. Die Sequenz muss in Länge, Reihenfolge, Fence-Art und byte-exaktem Body übereinstimmen; andernfalls bleiben beide Kopien unabhängig geprüft und die Paarungsprüfung meldet die strukturelle Abweichung.

`pnpm run verify-translation-pairing --list` gibt den aktuellen Paarungszustand jedes Dokuments im Geltungsbereich aus — missing, out-of-sync oder ok. Der Befehl schlägt nie fehl; Zeilen mit `missing` und `out-of-sync` benennen Verstöße, die die normale Prüfung zurückweist.

`pnpm run verify-translation-pairing <pair...>` prüft nur die benannten Paare — jede der drei Dateien eines Paares (oder sein bloßer Stamm) benennt es —, sodass eine Aktualisierungsschleife ihr eigenes Paar in Sekunden verifiziert, statt den Korpus erneut zu durchsuchen. Die argumentlose korpusweite Form ist das, was `doc-sync` und CI ausführen; ein bereichsbezogenes Grün ersetzt sie auf PR-Ebene niemals.

Die praktische Regel, die diese Prüfung erzeugt: **wenn ein PR eine der beiden Seiten eines gepaarten Dokuments bearbeitet, aktualisiert derselbe PR das Gegenstück direkt in einem terminologiegeleiteten Durchgang und protokolliert das Paar mit `--write <pair>` neu**, genau wie die bestehende doc-sync-Regel des Repos für Code und READMEs. Ein PR, der ein Paar nicht synchronisiert lässt, schlägt in CI fehl.

Die Grenze der Prüfung, klar ausgesprochen: **eine grüne Prüfung bedeutet, dass das Paar bei genau diesen Inhalten als konsistent bestätigt wurde, nicht dass die Bestätigung fundiert war.** Sie prüft Hashes und Markdown-Struktur; sie kann nicht beurteilen, ob beide Seiten dasselbe aussagen oder ob die Formulierung korrekt, gut terminiert und natürlich ist — das ist die Hälfte des Vertrags, die beim Reviewer liegt, gemäß [translation-rules.md](translation-rules.md). Ein neu protokolliertes Paar mit einem nachlässigen Gegenstück passiert die Prüfung; es darf die Review nicht passieren.

## Geltungsbereich und Ausnahmen

**Geltungsbereich**: die Wurzeldokumente `CONTRIBUTING.md`, `BRAND_GUIDELINES.md` und `SAFETY.md`, jedes Nicht-Vendor-README und jedes aktive Dokument unter `.agents/notes/**`, `docs/**` und `python/**`. Die README-Erkennung erfolgt unabhängig von Groß- und Kleinschreibung des Basisnamens und deckt künftige Verzeichnisse ohne weitere Manifeständerung ab. Abhängigkeits- und ignorierte Build-Output-Bäume sowie der eingefrorene Baum `.agents/notes/archived/` sind Ausnahmen der Erkennung, keine sich entwickelnde Übersetzungsquelle.

Generierte englische Referenzen und Graphen nehmen an der Paarung teil, wenn ein geprüftes chinesisches Gegenstück verfügbar ist. Ein Generator legt seine generierten Daten in generierten Bereichen ab und schreibt jeden Bereich in beide Seiten, sodass eine Neugenerierung nie eine manuelle chinesische Aktualisierung oder ein neues Protokoll erfordert; nur die Prosa außerhalb der Bereiche wird übersetzt und protokolliert. Freshness- und Paarungsprüfungen erzwingen ihre jeweiligen Invarianten unabhängig voneinander.

Gemeinsam genutzte generierte Bereiche, etwa die Cordis-Subsystem-Bereiche und die Paketbereiche des [Konfigurationskatalogs](../config-catalog.md), halten jedes generierte Byte über die Sprachen hinweg identisch, außer lokalisierten Pfaden gepaarter Dokumente; Bezeichner innerhalb eines Bereichs sind Code-Bezeichner und keine übersetzten Wörter. Ein Ganzseiten-Generator kann auch quelleneigene gepaarte Prosa wie [persistence-catalog-text.ts](../../scripts/persistence-catalog-text.ts) aus denselben strukturellen Daten mit übereinstimmender Markdown-Struktur und identischen Code Blocks rendern. Er generiert beide Seiten und ihr Konsistenzprotokoll zusammen neu; die Review überprüft weiterhin Bedeutung und Terminologie der gepaarten Prosa.

Generierte englische Quellen lassen den Sprachumschalter weg, den gewöhnliche verfasste Quellen tragen, weil das Hinzufügen den Generator veralten ließe; ihre chinesischen Gegenstücke verlinken weiterhin auf die englische Quelle zurück. Ein manuell gepflegtes chinesisches Gegenstück darf nur selbstreferenzielle Aussagen über Generierung und Pflege umschreiben, die für die geprüfte Übersetzung andernfalls falsch wären; der gesamte technische Inhalt unterliegt weiterhin den gewöhnlichen Treueregeln.

**Ausgenommen** (nie gepaart, und die Prüfung weist eine `.zh.md` oder `.i18n.yaml` dafür zurück):

- [cordis-api/inherited.md](../cordis-api/inherited.md) — generiert ohne geprüftes chinesisches Gegenstück, sodass beide Website-Locales die englische Quelle projizieren.
- `docs/AGENTS.md`, `.agents/notes/**/AGENTS.md` und deren `CLAUDE.md`-Instruktions-Symlinks — Agent-Instruktionen, die wie das Wurzel-`AGENTS.md` nur auf Englisch gepflegt werden.
- `docs/i18n/terminology.md` und [style-samples.md](style-samples.md) — beide sind konstruktionsbedingt zweisprachig.
- [translation-prompt.md](translation-prompt.md) — die Prompt-Vorlage der automatisierten Pipeline; ihr Body wird wörtlich von Maschinen konsumiert, sodass eine gepaarte Übersetzung das Verhalten der Pipeline ändern würde.
- [review-ownership/README.md](../../.github/review-ownership/README.md) — repository-interne Freigaberichtlinie, die nur auf Englisch gepflegt wird.
- `.agents/notes/archived/` — eingefrorene historische Tripletts. [`verify-archived-agent-notes`](../../scripts/verify-archived-agent-notes.ts) validiert ihre Vollständigkeit und Inhaltssiegel; die Übersetzungspflege darf sie niemals umschreiben.

**Universelle Anforderung**: Jedes aktuelle oder künftige Dokument im Geltungsbereich muss als vollständiges zweisprachiges Paar zusammengeführt werden. [scripts/translation-pairing.manifest.json](../../scripts/translation-pairing.manifest.json) enthält nur explizite Ausnahmen; es gibt keine dateibezogene Rollout-Liste, keinen Datumsstichtag und keine README-spezifische Richtlinienklasse.

## Arbeitsteilung

Routinemäßige Gegenstücke werden vom arbeitenden Agent direkt in einem Durchgang aktualisiert, nachdem er [terminology.md](terminology.md) geladen hat; er ruft keinen Übersetzungs-Skill auf, erzeugt kein Briefing, führt keinen separaten Übersetzungs-Review-Durchgang aus und delegiert nicht an einen Subagent. Der erweiterte Workflow [dsh-translate-docs](../../.agents/skills/dsh-translate-docs/SKILL.md) behält diese schwereren Mechanismen für die explizite Nutzeraufforderung. Die Prüfung kontrolliert Paar-Vollständigkeit, protokollierte Hashes, den chinesischen Rücklink und den Umschalter verfasster Quellen (mit der dokumentierten Ausnahme für generierte Quellen) sowie ihre dokumentierte strukturelle Signatur. Die Review besitzt weiterhin Übersetzungsqualität, Terminologie und strukturelle Anforderungen, die die Signatur nicht kodiert. Der Prompt-Vertrag ist ausführbar: [scripts/translation-prompt.ts](../../scripts/translation-prompt.ts) rendert die eingecheckte Vorlage (Terminologie injiziert; die Vorlage trägt ihre eigenen kalibrierten Regeln) in beide Richtungen und parst die Antwort mit drei Abschnitten, während `verify-translation-prompt` beide Render-Richtungen und das eingecheckte Beispiel in `doc-sync` durchspielt.
